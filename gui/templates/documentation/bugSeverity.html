Bug Severity - Test Strategyguide for testers

What is Bug Severity?

Severity is a measure of the impact a defect has on the system under test. It indicates how bad the impact is on the product, the business, or the users. Severity is classified after the defect is opened, based on how critical the impact is to the product's functionality. Severity is part of the Test Strategy: each project defines its own severity scheme and the meaning of each level.

ISTQB defines priority (how soon to fix) and severity (how bad the impact is) as two distinct concepts. Severity evaluates the defect's impact; priority evaluates the urgency of fixing it. In TestLink these are unified through the Test Strategy: each test case has an importance, each test-plan link has an urgency, and their product yields the priority.

Severity Levels

The standard severity scheme used in TestLink is based on four levels. Each severity level is part of the Test Strategy and its meaning is defined per project (see the Severity Configuration screen in the Projects section). The default scheme is:

CRITICAL
Blocks the product entirely; system crash, data loss, security breach, core function completely unavailable.
HIGH
Major functionality broken or severely degraded; a key feature unusable with no workaround.
MEDIUM
Moderate impact; feature partially broken or works with a workaround, wrong output in edge cases.
LOW
Minor impact; cosmetic issues, small usability problems, typographical or layout errors.

CRITICAL / HIGH / MEDIUM / LOW - these are the four severity levels.

Severity in the Test Strategy

Severity is defined as part of the Test Strategy of a project. The Test Strategy is the document/scheme that states the overall testing approach of a project, including risk management. The severity scheme is part of that strategy because it tells the team how important each test and each defect is.

In TestLink, the Test Strategy maps to three attributes captured across the test case and test plan:

AttributeWhere definedMeaning
ImportanceTest case version (tcversions.importance)How important the test case is to the product (Low/Medium/High).
UrgencyTest plan link (testplan_tcversions.urgency)How urgent the test case is within the current test plan (Low/Medium/High).
PriorityComputed (importance x urgency)The resulting priority used to prioritize execution and defect fix effort.
Priority = Importance × Urgency
The "Enable Priority" project option (Projects → Edit Project → Features) turns priority management on for a project. When disabled, priority is not tracked for that project.

Severity / Priority Matrix

With importance and urgency each in {Low=1, Medium=2, High=3}, their product ranges from 1 to 9 and is mapped to a severity/priority level:

  Urgency LOW (1) Urgency MEDIUM (2) Urgency HIGH (3)
Importance LOW (1) LOW (1) LOW (2) MEDIUM (3)
Importance MEDIUM (2) LOW (2) MEDIUM (4) HIGH (6)
Importance HIGH (3) MEDIUM (3) HIGH (6) CRITICAL (9)
Product < 3 maps to LOW, product >= 6 maps to HIGH (thresholds configurable in the Test Strategy), values in between map to MEDIUM. The CRITICAL level (9) is reached only when importance and urgency are both HIGH.

Severity in the Bug Lifecycle

When a defect is found, the tester assigns a severity to it in the bug report. Defects are triaged by severity: CRITICAL and HIGH defects are fixed first, MEDIUM defects are scheduled, and LOW defects are deferred. Severity travels with the defect through the bug lifecycle (New → Assigned → Fixed → Retest → Closed).

Severity measures impact on the product; priority measures urgency of fix. A cosmetic LOW-severity defect could still have HIGH priority if it blocks a release, but in the Test Strategy the severity scheme is fixed before testing begins.

Define Severity per Project

Because severity is part of the Test Strategy, each project can define its own severity levels and their meanings with the dedicated Severity Configuration screen. Open it from the Projects section (Project Management → Severity Configuration).
